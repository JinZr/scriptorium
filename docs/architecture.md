# Architecture

Scriptorium is a single-user modular monolith. It has no server, queue, or model runtime. Codex, Claude Code, and Antigravity CLI operate the same JSON CLI from their own selected model sessions.

## Authority and flow

- A Git commit and tree digest identify manuscript content. A disposable snapshot is scanned and compiled; uncommitted files are excluded.
- `manuscript.py` creates the frozen source, navigation, source map, PDF, and page-image bundle. Retrieval checks the requested source or page against its frozen digest; result submission validates the complete bundle.
- `workflow.py` prepares review, revision, and verification tasks. It validates whole structured submissions and advances only after the required prior stage and human decision.
- `storage.py` owns SQLite migrations, tasks, attempts, decisions, and events. `artifacts.py` publishes immutable SHA-256 content.
- `service.py` serializes per-run mutations and retrieval under an OS file lock. A task claim persists across CLI processes. `cli.py` provides the shared JSON interface.

Explicit `manuscript.supplements` add independent LaTeX entrypoints from the same commit. Each entrypoint's
dependency closure is scanned separately, preserving its graphics and bibliography context; the bundle freezes
their union. Builds use separate disposable copies so generated files cannot leak between documents. The main
PDF and each supplement are concatenated in configured order into the existing `manuscript.pdf` evidence space.
Both the manifest and source map freeze a document index of entrypoint, first global page and page count. Its
ranges must partition the review PDF and refer to distinct frozen text sources. Indexed retrieval checks this
mapping against the immutable bundle metadata. Revision and verification use the same document configuration
and rebuild the entire set. Any failed document blocks that stage.

`run start` freezes inputs, compiles the base bundle, and creates review tasks. Task preparation stores a content-addressed file index for the bundle. `task claim` records the external client, model, effort, and session ID on a durable attempt. The CLI claim and default show return a compact overview with input digests and retrieval commands. `task show --part prompt|schema|source-map` returns frozen text fragments bound to their digests and the attempt input. Source-map fragments contain the original bundle file bytes decoded as UTF-8. Show remains available for terminal attempts without reopening material retrieval or workflow state. `tool_output.py` sizes both compact JSON success envelopes and ordinary indented output, including UTF-8 encoding, escaping, metadata, and newline, to at most 7,000 bytes for claim, show, read, search, nav, and page. It supplies lossless continuation commands; the CLI uses the same serializers and preserves the current output mode in emitted continuations. Input access events record only the fragment offsets returned, rather than implying the full prompt or schema was displayed.

The CLI also projects run mutation results into bounded acknowledgements, preserving the operation's returned state without a second database read after the mutation lock is released. `run status` holds the run lock while collecting a compact overview and current next actions. Detailed task history and frozen configuration remain in the complete report. `run report --part` holds the same lock while validating and rendering a report section into bounded canonical-JSON text fragments. Each continuation binds the entire report digest; changes between calls require a restart. Report reads write no workflow events or snapshot artifacts. Full JSON/Markdown exports and the internal `get_run` representation retain their complete data.

`task read`, `task search`, `task nav`, and `task page` check the indexed metadata and requested files without loading unrelated sources or pages, then return bounded frozen material and append access events. Byte limits are applied before recording access: read events record the resolved source identity, source digest, exact returned line and character-offset ranges, and continuation cursor; search events include only returned matches. `task submit` stores the raw result, validates it against the frozen schema and evidence map, and records a complete or failed attempt. `task submit --check` runs the same validation under the run lock without storing output, a validation report or attempt status; it appends only a `tool.submit_check` event. An accepted result is replayed into findings, a candidate patch, or verification. Repeating a completed submission returns the same receipt; a different or superseded result is rejected.

`task export` is the one retrieval command that writes outside Scriptorium's state: it copies the attempt's frozen bundle files (sources at their `read_path`, `manifest.json`, `navigation.json`, `source-map.json`, `manuscript.pdf`) into a new or empty host directory. Each file is verified against the bundle index, written atomically and read-only, and confined to that directory; a failure removes what the call wrote. A `tool.export` event binds the sorted paths and digests to the attempt. An export does not change the evidence contract: anchors cite frozen source paths, digests, and lines, and `task read --anchor` yields a verified anchor. The coverage audit keeps three states per declared range, read through the CLI, `exported` without a read return, or `declared_without_access`, and `review_tool_access` counts exports; none of them proves comprehension or that a page was viewed.

A CLI process ending does not interrupt an external attempt. Only explicit abandonment, retry, or cancellation changes that claim. An invalid result creates a durable validation report; retry must be requested explicitly. Each attempt binds its own prompt, schema, and bundle digest, including correction prompts. A later finding waiver interrupts an active revision or verification task whose frozen prompt no longer matches the decision context; `run resume` prepares a new task. On recovery, completed output is read from the artifact store and validated again before domain records are materialized. Missing or corrupt frozen material is an infrastructure failure.

New review output includes a structured, model-declared scope: completion status, checked and outstanding frozen source regions or PDF pages, and limitations. Submission validates declared paths and ranges against the attempt bundle. Parsing selects the supported review model from stable fields in the run's frozen schema; old external review outputs retain their original two-field contract on replay. Reports read accepted output artifacts for declarations and summarize successful task-tool returns independently for every review attempt, including failed attempts. A read-only audit compares the latest accepted scope with cumulative returns through that attempt, listing read-line fragments, search matches, page paths, and checked text or pages without matching task-tool returns. Non-text source paths are marked incomparable; direct host access remains invisible. Historical SDK runs mark tool-access counts unavailable. An unsupported frozen review schema fails explicitly. Scope is not a measured coverage score. Its `complete` declaration determines whether the review role has finished; it does not establish that the host read or understood every relevant item.

New substantive-review tasks use a distinct frozen output schema. Their `claim_checks` record anchored evidence, a critical question, a countercheck, an assessment, and links to retained findings by output index. New runs also freeze explicit judgment fields: the claim's stated scope, the check type, the answer to the critical question, the exceptions found, and an optional recomputation. Schema validators reject an assessment that contradicts its declared answer, exceptions, or recomputation outcome. New runs also freeze a claim inventory. Each entry is a central claim, anchored where the authors state it; each claim check names one entry by `claim_index`, and an entry no check names gives a reason it was not checked. Validators require every index to name an inventoried claim and a complete review to check every headline claim. A `blocker` finding must be linked from a check of a headline claim, and the substantive `verdict` must agree with the review's findings: `reject` or `major_revision` needs a `major` or `blocker` finding, counting a continuation's earlier recorded findings, and `accept` allows none. The output model follows the frozen schema, so runs frozen before these fields keep their earlier shape. Submission validates the anchors, including each claim anchor, and the links before accepting any finding. The report presents the checks alongside scope and tool returns; the checks remain model declarations, not proof that the model reasoned correctly.

New review tasks also freeze a consequence-based severity rubric. The workflow adds it once to every review role's frozen prompt template, beside the evidence-anchor and scope instructions, so the prompt digest and attempt input digest bind it; the role prompts do not repeat it. The output schema publishes the same level definitions on the finding's `severity` and requires a non-blank `consequence` stating what a reader would wrongly believe, or be unable to do, if the problem is not fixed. A `submission_compliance` finding (checklist answers, page or figure limits, anonymity, template rules) must be `minor` or `suggestion`. New copyedit, consistency, and figure-review findings at `moderate` or above name an `affected_claim`; it stays in the attempt's output artifact rather than the findings table. Severity remains a model declaration: validation checks the compliance ceiling, not whether a level fits. The consequence is stored in a nullable findings column added by a numbered migration when an external-run database is opened, or with the external-task migration when a new run upgrades a legacy database; legacy findings read with no consequence. The output model follows the frozen schema, so runs frozen before the rubric accept and replay findings without a consequence, with their original fingerprints. The release gate is unchanged; its severity check still covers only undecided `blocker` and `major` findings.

For scoped external reviews, a `partial` or `unknown` declaration leaves the review stage incomplete. Explicit `run continue` reopens only that completed review task while the run remains in review or awaits finding decisions. It retains the accepted attempt and findings, then binds the next claim to a new prompt digest with the previous scope and finding IDs. A completed continuation replaces the role's current scope declaration, while earlier outputs remain in the report. Duplicate findings keep their original identities and decisions. A run frozen with the older unscoped review schema follows its original completion behavior. The required-review gate checks the latest accepted declaration while the run remains in review or awaits decisions. Runs that already advanced beyond those stages retain their prior review-completion standing; every accepted review output artifact must still validate. Tool returns are never proof of comprehension.

Read, search, and page operations hold the run lock through their access event, so cancellation or submission cannot terminalize an attempt between its active-status check and the returned material. The external-schema upgrade rechecks the database version inside a SQLite write transaction, allowing concurrent new runs to share one migration.

## Evidence and gates

Text evidence uses a bare source path, source digest, inclusive line range, and verbatim quote. New runs freeze one line definition as the evidence contract's `line_terminators`, shared by retrieval, source-map line counts, evidence validation, exact edits and patch diffs: a line ends only at `\n`, `\r\n` or `\r`, so form feeds and Unicode line separators stay inside their line. A run whose frozen contract predates that field keeps `str.splitlines()` numbering for its line counts, validation, replay, edits and diffs; its retrieval can still number such a file differently, so review it in a new run. The source map's `line_count` bounds anchors; the manifest's per-source `lines` value is informational. PDF evidence uses `manuscript.pdf` plus a 1-based page; a page-image path is only a read location. Tool access logs report material returned, not model comprehension or exhaustive coverage.

`task page --document ENTRYPOINT --number N` resolves a document-local physical page into that global PDF page.
The response and access event record both coordinates. Zoomed page views are derived renders of the digest-checked frozen PDF, stored outside the bundle under their own digest and never overwritten; the PDF text layer is a reading aid whose continuations are bound to one extraction by its digest. Neither changes the evidence contract. Scope, evidence and coverage audits continue to use global
pages, so separate documents' first pages cannot be conflated. The document index is frozen bundle metadata;
it does not change the submitted result schema or require a database migration.

Finding decisions, patch approval, verification, and application are separate stages. The verifier must claim from a new host-reported conversation ID, distinct from review and revision. A declared or reused ID cannot produce a passing verification. This checks recorded provenance; Scriptorium cannot authenticate the external host's claim. Patch application rechecks exact approved edits against the current worktree. Infrastructure failures cannot pass the release gate.

External model usage and cost are unknown unless the host supplies independent evidence. The tool neither invokes providers nor enforces their spending limits. Historical internal-SDK runs remain available for read-only status, reports, and gate inspection, without conversion to external tasks. Opening a legacy database for those queries does not apply the external-task migration; starting a new external run applies it only when no historical run still requires the original version.
